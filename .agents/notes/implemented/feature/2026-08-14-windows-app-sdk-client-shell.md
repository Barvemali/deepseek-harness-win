# Agent Note: Windows App SDK client shell

Status: implemented

English | [中文](2026-08-14-windows-app-sdk-client-shell.zh.md)

## Problem

The dsh Web GUI only launches from a terminal: run `dsh web`, then open the printed URL in a browser. There is no desktop entry point, and the only prior desktop consideration — an Electron shell loading dist over `file://` and carrying fetch over an IPC bridge — never shipped and would require a custom transport.

## Decision

`apps/windows/DshShell` is an unpackaged WinUI 3 shell (Windows App SDK 2.4, .NET 10 on `net10.0-windows10.0.26100.0`, x64, self-contained WinAppSDK runtime) that embeds the existing `dsh web` server output in a WebView2 control. On launch it probes the configured URL (default `http://127.0.0.1:3080`), spawns the configured launch command when nothing listens, waits until the URL answers, and loads the page. The default command is the root `dsh` script's own invocation — `node --import tsx/esm apps/cli/src/bin.ts web --no-open` — run in the repository root (located by walking up from the executable to `pnpm-lock.yaml`); it deliberately bypasses pnpm, whose dependency-status check and corepack shim both prompt on a no-console spawn, and passes `--no-open` because the shell replaces the browser. Since dsh 0.1.3-alpha.1 the server requires the per-boot process token it prints on its readiness line (`dsh web: http://…/?token=…`) to mint the browser cookie, so the shell captures that token from the server output and navigates to the authenticated URL when it spawned the server; attach mode relies on the cookie a prior spawn left in the persistent WebView2 profile. Closing the window kills only the process tree the shell started; attaching to an externally running server leaves it alone.

The page is always served by `dsh web`: only that server injects `window.__DSH_BOOT__`, so the WebView2 loads the served page and the trust fence, `/api` bridge, and boot injection stay untouched. At every launch the shell clears the WebView2 HTTP cache (`Network.clearBrowserCache`): `dsh web` serves `index.html` without cache validators, so the persistent profile would otherwise keep serving a stale GUI whose old bundle revs call old RPC contracts after a git pull rebuilds the dist. A WebView2 renderer can also stop painting and stop answering input while the rest of the window keeps working, which leaves a window that looks alive and ignores every click; `Reload` cannot repair it, because the frozen process is the one that would perform the reload. The shell therefore runs a 10-second watchdog that calls `ExecuteScriptAsync` with a 5-second answer deadline and treats a recent navigation as in flight: one missed answer reloads the page, three consecutive misses rebuild the view by closing the control and creating a new one over the same server URL, and `CoreWebView2.ProcessFailed` reloads after a renderer, GPU, or frame process failure and rebuilds after `BrowserProcessExited`. A rebuild never touches the server process, so it cannot cost the sessions a running server holds; the "Rebuild view" toolbar button and Ctrl+Shift+R run the same rebuild on demand, and navigation, process failures, and rebuilds are logged beside the server output. Settings persist at `%LocalAppData%\DshShell\settings.json`; shell and server output share `%LocalAppData%\DshShell\server.log`; a single-instance mutex prevents two windows from fighting over one server process. `apps/windows` is deliberately not a pnpm workspace member (no `package.json`), so the release-member and constraint gates never see it.

The spawned server runs non-interactively: the shell sets `COREPACK_ENABLE_DOWNLOAD_PROMPT=0` (a corepack shim on PATH would otherwise hang on "Do you want to continue? [Y/n]" when the pinned pnpm version is not cached) and `npm_config_verify_deps_before_run=false` (pnpm 10+ runs a dependency-status check before scripts and prompts "The modules directories will be removed and reinstalled from scratch. Proceed?" when a git pull changed the lockfile; `confirmModulesPurge` does not cover that check). A launch that fails before readiness reports its exit code in the status bar and names the repair in a dialog, derived from the last 60 server output lines the shell kept: `MissingClientBundleError` asks for `pnpm install`, `pnpm run build:lib`, and `pnpm run build:web`; an unresolved module asks for `pnpm install`; a failed bind or write names the port or the data directory. `dotnet build` resolves the `resources.pri` MSBuild tasks into the .NET SDK folder, which lacks `Microsoft.Build.Packaging.Pri.Tasks.dll`; an `AppxMSBuildToolsPath` fallback in `DshShell.csproj` points at the Visual Studio install that carries it (building with the Visual Studio `MSBuild.exe` needs no fallback).

## Alternatives considered

**Electron over `file://` + an IPC fetch bridge.** Rejected: the bridge does not exist and would be a new transport to build and trust, and the Electron mentions in the codebase never shipped.

**A Tauri or other WebView2 wrapper.** Rejected: C# + WinUI keeps one Windows-native stack, and WebView2 is already a Windows platform component, so the extra toolchain buys nothing here.

**Keep the terminal-plus-browser workflow.** Rejected: the point of the shell is a desktop launch without a terminal.

**MSIX packaging.** Rejected for the first iteration: unpackaged plus self-contained WinAppSDK keeps `dotnet build` and direct exe launch; packaging can layer on later.

## Consequences

The shell needs Windows with the WebView2 runtime, a Visual Studio install for `resources.pri` generation under `dotnet build` (or the VS `MSBuild.exe`), and a built frontend `dist/` — the same prerequisite `dsh web` itself has. Both lib faces are required, in order: `pnpm run build:lib` runs the host pass that emits the Typert declarations (`lib/typert.host.d.ts`, `lib/typert.remote-client.d.ts`) the client typecheck consumes, so `pnpm run build:lib:client` alone fails with unresolved `/remote` modules and never reaches the bundle pass. A pull that deleted a package also leaves that package's `lib/` behind in a directory without `package.json`, which the bundling pass still reads and fails on with `MISSING_EXPORT` until `pnpm run clean` removes it. When the shell spawns the server, it owns that process tree's lifetime; users who already run `dsh web` get an attach-only window. The non-interactive spawn flags mean the first launch after a git pull can take longer while pnpm reinstalls the changed workspace.
